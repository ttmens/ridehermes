# CONTEXT.md - 项目背景与决策

## 项目起源

### 问题陈述

现有打车平台存在以下问题：
1. **交互繁琐**：乘客需要手动输入地址、选择车型、确认订单
2. **AI 集成困难**：开发者想在自己的 AI 产品中集成打车功能，但没有标准接口
3. **语音叫车缺失**：市场上缺少真正可用的语音叫车产品

### 解决方案

RideHermes = **AI-First 出行平台**
- 语音优先：乘客可以说"帮我叫辆车去机场"
- MCP 标准：AI 智能体通过标准协议调用打车能力
- 全栈自研：从后端到移动端完整实现

## 关键决策

### 1. 为什么选择 Go 作为后端？

**决策**：使用 Go + Gin + GORM

**理由**：
- 高并发：打车场景需要处理大量实时位置更新
- 部署简单：单二进制文件，无需运行时依赖
- 生态成熟：Gin (HTTP) + GORM (ORM) 组合稳定可靠

**替代方案**：Node.js（类型安全弱）、Python FastAPI（性能不如 Go）、Java（开发效率低）

### 2. 为什么选择 Flutter 做移动端？

**决策**：乘客端 + 司机端都用 Flutter

**理由**：
- 跨平台：一套代码同时生成 Android + iOS
- 性能接近原生：比 React Native 更流畅
- 地图集成：高德地图 Flutter 插件成熟

### 3. 为什么选择高德地图？

**决策**：统一使用高德地图

**理由**：
- 国内覆盖：POI 数据最全
- API 稳定：服务可用性高
- 价格合理：商业授权费用可接受

### 4. 为什么实现 MCP Server？

**决策**：提供 MCP (Model Context Protocol) 接口

**理由**：
- AI 趋势：Claude、Hermes 等 AI 智能体需要工具调用能力
- 标准化：MCP 正在成为 AI 工具调用的事实标准
- 差异化：竞品（DiDi）尚未全面提供 MCP 接口

### 5. 为什么使用 Redis 做位置缓存？

**决策**：司机实时位置存储在 Redis

**理由**：
- 读写极快：位置更新频率高（每 3-5 秒）
- 过期自动清理：司机下线后位置自动失效
- Geo 支持：Redis GEO 命令支持附近搜索

## 假设与风险

### 已验证假设

| 假设 | 验证方式 | 结果 |
|------|----------|------|
| Flutter APK 可编译 | 实际编译 | ✅ 通过 |
| Go 后端架构合理 | 代码审查 | ✅ 通过 |
| 高德 API 稳定 | 实际调用 | ✅ 正常 |

### 待验证假设

| 假设 | 风险 | 缓解措施 |
|------|------|----------|
| AI 意图理解准确率 > 90% | 用户体验差 | 先做 MVP，收集真实语音数据 |
| MCP 协议被广泛采用 | 开发投入浪费 | 同时保留 REST API |
| 司机愿意使用新平台 | 供给不足 | 先小范围试点 |

## 约束条件

- **地图服务**：只能使用高德或百度（用户明确要求）
- **部署环境**：阿里云/腾讯云，国内网络
- **开发团队**：1 人（全栈）
- **合规**：需要网约车运营资质
