# 1　概述与设计原则

**产品定位。**灵犀智能是坤智科技推出的、面向计划性出行（预约与计划性场景）的 AI 原生出行平台，底层构建在 A2A（Agent\-to\-Agent）协议之上。它与实时派单平台有本质区别：不做秒级实时调度，只服务时间预算为分钟到天级的计划性出行。这一范围边界是整套架构成立的前提，贯穿本文全部章节。

**商业与技术的同构。**在商业模式上，平台以供给侧 SaaS 订阅替代传统的按单抽佣；在技术上，这对应「薄中心不抽佣、厚边缘自主决策」的结构。本文描述的技术架构不是商业模式的附属物，而是与之同构的一体两面。

## 1\.1　什么是「AI 原生」

「AI 原生（AI\-native）」与「AI 增强（AI\-enabled）」是两种根本不同的系统组织方式，区分二者是理解本方案的钥匙。

**AI 增强：**在传统中心化系统之上叠加 AI 功能，例如用机器学习模型优化中央派单。智能是中心的一个模块，系统的骨架仍是中心化的。

**AI 原生（本平台）：**系统最基本的构件就是自主 Agent。匹配、定价、协商、调度由分布在边缘的 Agent 以各自策略自主完成；中心退化为只负责协议、信任与清算的薄层。智能不是一个被调用的功能，而是系统的组织方式本身。

由此推出三个直接结论：可组合（Agent 即构件，新增一类供给等于新增一个会说协议的 Agent，而非改造中心）；可演进（边缘策略可独立迭代，互不阻塞）；低中心算力（系统中不存在一个常驻的全局实时优化器）。

|**维度**|**AI 增强（传统平台 \+ AI）**|**AI 原生（灵犀智能）**|
|---|---|---|
|智能位置|中心的一个模块|系统的组织方式|
|匹配 / 定价|中央引擎计算|边缘 Agent 自主协商|
|中心角色|撮合大脑|协议 · 信任 · 清算的薄层|
|新增供给类型|改造中心逻辑|接入一个新 Agent|
|中心算力随单量|线性增长|近似常数|



## 1\.2　核心设计原则

以下三条原则贯穿全文，是所有具体设计的上位约束。

**原则一　薄 / 厚边界判定法则。**一个功能只有在「去中心化会破坏 互操作 / 信任 / 终局性 / 可问责 四者之一」时，才允许进入薄协调层；否则一律下沉到厚边缘层。本法则在第二章详述，并在全文反复使用。

**原则二　智能上薄、责任上厚。**中心不放任何业务智能——不撮合、不排序、不定价；但在身份背书、资金清算、审计存证、法定合规上必须扎实地集中。「薄」指的是不持有业务智能，不等于不担责。

**原则三　协议不是护城河。**架构假设 A2A 协议会被标准化甚至开放（尤其在与监管共创之后）。竞争力来自「在标准之上做信任度最高的运营方」、OEM 联盟关系与监管共创位置，而非协议保密或数据独占。数据资产仅作为冷启动加速器，不作为护城河。

# 2　总体架构：薄协调层 \+ 厚边缘层

整套系统分为两层：中心是「薄协调层」，只做登记、会合、清算、审计；外围是「厚边缘层」，由自主 Agent 承载全部业务智能，彼此点对点协商。下图给出分层与消息流的总览。



|**薄协调层（中心）**<br>身份 · 会合 · 清算 · 审计　【约束：不撮合 · 不排序 · 不定价】||
|---|---|
|**① 意图 · 发现　（上行 / 下行）**|**③ 缔约 · 清算　（上行 / 下行）**|
|**需求 Agent**<br>企业 / 酒店（承重）· 策略 · 预算 · 批量调度|**供给 Agent**<br>司机 / 车队 / Apollo · 报价 · 排程 · 接单策略|
|**② 点对点协商（报价 · 还价）—— 撮合发生在边缘，不经中心**||

*图 1　薄协调层 \+ 厚边缘层：仅 ①③ 触达中心，② 撮合在边缘*

图中只有两类消息触达中心：① 意图发现与 ③ 缔约清算；真正承载撮合的 ② 点对点协商完全发生在边缘、不经过中心。这正是「薄」的全部含义。

## 2\.1　边界划分法则

判断一个功能该留在中心还是下沉边缘，只用一条测试：把它去中心化，是否会破坏以下四者之一？是，才进薄层；否则下沉边缘。

- **互操作：**没有共享标准，Agent 之间无法通信。

- **信任：**没有第三方背书，没有一方会接受对手方的自我声明。

- **终局性：**必须有一个权威记录认定「这笔交易确实发生」。

- **可问责：**监管与争议需要单一可信来源。

按此法则逐项落点如下表。注意定价、排序、偏好匹配、接单决策全部不满足任一测试，因此一律在边缘。

|**功能**|**落点**|**依据**|
|---|---|---|
|身份与能力背书|薄层|信任|
|协议与本体|薄层|互操作|
|会合与发现（仅硬约束）|薄层|互操作 · 可问责|
|清算与结算|薄层|终局性|
|账本 · 审计 · 仲裁|薄层|可问责|
|合规硬闸门（法定上限）|薄层|可问责|
|排序 / 推荐|**边缘**|不满足任一测试|
|定价|**边缘**|不满足任一测试|
|偏好匹配|**边缘**|不满足任一测试|
|接单决策|**边缘**|不满足任一测试|



## 2\.2　与中心化派单架构的对比

与行业在位的中心化派单平台相比，本架构的差异不在算法优劣，而在结构。中心化派单是「厚中心 \+ 薄边缘」：撮合在中心，司机只是接收订单的端点；其中心算力随订单量线性增长，且平台天然承担撮合责任、靠按单抽佣获利。本平台反之。

|**维度**|**中心化派单**|**灵犀智能**|
|---|---|---|
|撮合位置|中心|边缘|
|中心算力随单量|线性增长|近似常数|
|撮合责任|平台承担|边缘自主 \+ 中心硬约束|
|收入模型|按单抽佣|供给侧订阅|
|适用场景|实时调度|计划性出行|
|时延预算|秒级|分钟至天级|



**结构性结论：**「薄」既是技术选择，也是商业护城河——薄中心不抽佣，因此不会触发困住在位巨头的那个 P\&L 自我颠覆矛盾。薄，本身就是战略。

# 3　薄协调层设计

薄协调层是系统的「管道」，不是「大脑」。它做且只做以下六件事。

## 3\.1　身份与能力背书

每个 Agent（司机、车辆、车队、企业客户）持有可验证凭证（DID 风格）。中心只背书客观可核验的事实——三证合规状态、累计完单数、取消率、结算履约记录——并对其签名发布。

**关键克制：**中心不计算「评分」、不对 Agent 排名。事实由中心签名发布，「这意味着什么」留给边缘 Agent 自行解读。一旦中心评分，就开始承担撮合责任，也开始让中心算力随订单量增长。

## 3\.2　协议与本体

中心定义两样东西：A2A 报文语法，与出行意图本体。这是与交通主管部门共创、并向 OEM 联盟推行的「标准」本身。

|**报文**|**方向**|**语义**|
|---|---|---|
|Intent 意图|需求 → 中心 → 广播|声明一次计划出行需求|
|Offer 报价|供给 → 需求|对意图作出供给应答|
|Counter 还价|双向|多轮议价|
|Commit 缔约|双签 → 中心|达成并记录合同|
|Settle 清算|完单 → 中心|走资金、更新事实|



**出行意图本体包含：**时间窗（最早 / 最晚上车）、起讫点、车型、服务等级（语言 / 无障碍 / 隐私级）、价格上限、周期模式。

## 3\.3　会合与发现

给定一个意图，中心返回满足硬约束（时间窗内地理可达、合规匹配、能力匹配）的候选供给集合——无序、且不按软偏好过滤。中心是电话簿，不是红娘。该服务绝不排序，详见第八章护栏。

## 3\.4　清算与订阅计费

中心记录已缔约合同（双签的 Offer 至 Commit），并在完单时走资金，同时运行供给侧 SaaS 订阅计费。由于没有按单抽佣逻辑，本平台的结算显著轻于中心化派单。

## 3\.5　账本、审计与仲裁

中心维护不可篡改的 append\-only 全量流水（Intent / Offer / Commit / Settle），对接面向监管的上报接口。争议基于双方签名的记录裁决，而非中心的主观意见——这也是「智能上薄、责任上厚」的体现。

## 3\.6　合规硬约束准入

法定合规（含疲劳驾驶 / 法定服务时长上限）在会合与缔约环节执行二元准入：拒 / 不拒。它与中心本就在做的「合规硬约束过滤」属同一类动作，不构成撮合、不构成排序。其数据来源与机制详见第八章。

# 4　厚边缘层设计

全部业务智能——定价、排程、偏好匹配、接单决策——都在边缘 Agent 内部。

## 4\.1　Agent 模型（三类角色）

Agent 按角色而非行业划分为三类：需求 Agent、供给 Agent、渠道 / 生态 Agent。前两类是核心，下文展开。

## 4\.2　需求 Agent（B 端承重柱）

需求 Agent 跑在企业 / 酒店等机构客户侧，内置出行政策（谁可使用哪个车型）、预算规则、周期模式（如酒店接驳、企业通勤）与批量排程。

**为何 B 端在架构上被特权对待：**机构需求可预测、可批量、政策驱动——这恰恰是边缘协商能够跑通的前提。C 端临时需求很难良好地 Agent 化，这是需求架构压在 B 端的技术理由，而不仅是商业理由。

## 4\.3　供给 Agent

供给 Agent 跑在司机 SaaS（人类司机）、车队管理系统（B 端车队）或 Robotaxi 控制器（如 Apollo）中，内置可用日历、定价策略、约束偏好与接单策略。它接收意图广播，自主决定是否报价、以何价报价、是否多轮还价、最终是否缔约。

## 4\.4　信誉解释在边缘

每个 Agent 用自己的模型去解读中心发布的客观事实——企业 Agent 可能重取消率，价格敏感方可能重报价。「什么是好匹配」的判断永远在边缘。

## 4\.5　Agent 的运行与隔离

**责任边界，而非物理边界。**现实部署中，这些 Agent 大概率运行在平台云端的多租户隔离进程内，而非真的跑在司机手机上。「边缘」首先是一条责任与自主的边界：每个 Agent 以自己的策略自主代表其委托方行动、且中心不做匹配决策；至于物理上跑在何处是部署细节。这一区分关乎技术尽调中的诚实表述：本平台不会向投资人宣称「我们没有技术成本」。

# 5　AI 原生核心：Agent 智能与算力分层

本章回答两个尽调必问的问题：AI 原生在工程上具体意味着什么？以及，靠 LLM 做协商，单位经济是否会被推理成本压垮？

## 5\.1　决策分层：99% 确定性 \+ 1% LLM

如果每一次匹配都在双方调用 LLM 推理，单位经济会崩。本平台的设计是：约 99% 的决策走确定性策略与规则（可用性、价格区间、硬约束），LLM 推理仅保留给新颖、高价值或歧义场景。LLM 调用率本身被作为一项成本 KPI 持续监控。

|**决策类型**|**计算方式**|**典型占比**|**成本量级**|
|---|---|---|---|
|常规报价 / 接单|确定性规则|约 95%|极低|
|边界议价 / 约束权衡|轻量启发式|约 4%|低|
|新颖 / 高价值 / 歧义|LLM 推理|约 1%|可控|



## 5\.2　协商引擎

协商引擎支持多轮报价与还价，并带收敛策略（轮次上限、出价步长、超时回退）。计划性出行分钟至天级的时间预算，正是允许这种异步多轮协商存在的根本前提。

## 5\.3　记忆与学习

边缘策略可在线学习历史协商结果以改进出价与接单。平台早期沉淀的运营数据在此作为冷启动加速器使用——它降低初始策略的盲目性，但不构成护城河（见原则三）。

## 5\.4　评测与可观测性

Agent 行为以评测集回归：任何协商策略变更必须通过既定评测基线方可上线。这与第十章的 AI 原生工程方法直接衔接。

# 6　A2A 协议与协商生命周期

## 6\.1　端到端时序

一次完整的计划性出行协商如下：

1. 需求 Agent 发出 Intent；

2. 中心①返回满足硬约束的候选供给集合（无序）；

3. Intent 广播至候选供给；

4. 愿意承接的供给 Agent 返回 Offer（价格、精确时间、车辆）；

5. 需求 Agent 按自身政策与边缘信誉模型评估，必要时 Counter 还价（②全程边缘点对点，不经中心）；

6. 收敛后双方签名 Commit，中心③记录合同；

7. 行程执行（边缘，中心不介入）；

8. 完单后 Settle，中心③走资金并更新客观事实。

中心只触达 ①③ 两步，其余全是边缘对边缘。这就是「薄」的运行态证据。

## 6\.2　为什么只服务计划性出行

这套薄 / 厚划分只在计划性出行成立，原因是结构性的，不可绕过。

**实时调度：**时延预算是秒级，Agent 没有时间做多轮异步协商；且全局最优（最小化全网等待）必须一个中央优化器——那必须是厚中心。

**计划性出行：**时间预算是分钟到天级，Agent 能够异步多轮协商；优化是逐单 / 逐批而非全局实时，边缘即可求解。

**不可动的边界：**一旦业务飘进实时调度，薄中心立刻坍塌，平台被迫重建为厚中心——也就是变回中心化派单，整个产品命题报废。因此「A2A 只服务计划性出行」是一条架构红线。

# 7　人机混合调度（Apollo / Robotaxi 集成）

人机混合调度是本架构的一处优雅之处：Robotaxi 车队只是另一个供给 Agent。计划锁定在 2026 Q4 与百度 Apollo（萝卜快跑）落地。

## 7\.1　Robotaxi 作为供给 Agent

Robotaxi 车队向系统广播自己的能力（自动驾驶、ODD 地理围栏、车型），并在其 ODD 内应答意图。需求 Agent 不关心报价来自人还是机器——同一套协议。

## 7\.2　适配器（shim）设计

现实约束是：Apollo 不会原生地说本平台的 A2A 协议。因此需要一个适配器（shim），将萝卜快跑现有的派单 API 包装成一个标准供给 Agent。该适配器在边缘（属于 Apollo 侧 Agent），不在中心——它是真实工程量，但不破坏薄中心。

## 7\.3　ODD 边界与人机接力

当一个计划行程的路径中途驶出 Robotaxi 的 ODD 时，由需求 Agent 侧进行路径分解，将超出部分回落到人类供给。该接力逻辑是真实的工程难点，须在阶段二专门验证，不可低估。

# 8　安全、合规与数据治理（以疲劳驾驶为例）

疲劳驾驶是检验本架构是否自洽的关键案例：它要求中心掌握司机的全局状态，而单平台账本天然只看得到流经自己 Agent 的那一片。本章给出完整解法。

## 8\.1　疲劳真相的数据来源

司机疲劳是其跨平台的全局状态。靠自己的订单账本判疲劳，等于让在多个平台分别接单的司机两边的休息提醒都不触发。因此真相不能从订单账本里长出来，必须来自一个平台无关的源头——车，以及主机厂车联网。车不在乎订单来自哪个 App，它只知道自己何时在运动。

**车的数据不等于司机的数据。**T\-Box 告诉你「这辆车被开了 10 小时」，不是「这个司机开了 10 小时」。网约车双班车普遍，10 小时车辆运动可能是两个司机各 5 小时；也存在一个司机换车的情况。因此必须在车辆遥测之上叠一层人车绑定（DMS 人脸识别 / 一人一车登记 / 登录会话与交班事件），才能把车辆状态真相转化为司机疲劳真相。

|**数据融合（登记）**<br>绑定 人 · 车 · 会话 → 累计服务时长（签名事实）||||||

*图 2　疲劳真相：数据融合 → 中心二元硬闸门 / 边缘策略*

**中心硬闸门（到法定上限）：**累计服务时长一旦触及法定上限，中心必须在会合 / 缔约环节直接拒绝——不把疲劳司机返回候选、不记录会违规的合同——而不是发布完事实就指望边缘自觉。在我国，疲劳驾驶的安全责任落在平台，监管不会接受「中心只发布事实、由司机的 Agent 自行决定继续」。

**边缘策略（上限以下）：**法定上限以下的疲劳管理（提前自愿休息、疲劳感知排程）是边缘 Agent 自己的策略生意。因为做的是计划性出行，平台可以在准入时就做疲劳感知的提前判断，而不是临场救火。

**关键不变量：**这道闸门必须是二元的（拒 / 不拒），绝不能演化成「司机疲劳度评分」。一旦中心开始算「A 疲劳 30%、B 60%，优先推 A」，就是在用安全当借口给司机排名，中心随即变厚，撮合责任与算力一起回流。线就划在这里：到法定上限是中心的二元硬闸门；上限以下的预测性管理是边缘的事。

## 8\.3　派生事实摄入原则（PIPL \+ 薄）

中心摄入只取派生事实（累计时长、疲劳标志），不取原始视频流与轨迹流；原始流留在车端 / 主机厂侧，平台只接经过签名的结论。这一刀同时守住 PIPL 合规与「薄」。反过来，若平台汇聚全量行车视频，既是合规雷，也破坏了薄中心。

## 8\.4　跨平台司机时长清分（两步走）

**现阶段：**事实来自主机厂 per\-vehicle 遥测 \+ 人车绑定，现在即可落地、且因为是真车而难以伪造，作为地面真相与反作弊锚点。

**终局：**跨平台的司机服务时长清分——由监管牵头、各平台上报，直接度量司机跨全平台的累计时长，堵死换车 / 多平台漏洞。这正是与交通主管部门共创的位置可以去定义的标准；一旦落地且由平台参与定义，它是一条真正的监管护城河，与原则三一致。

# 9　工程不变量与护栏

以下不变量是本架构的承重结构。每一条都附上违反后果，供技术尽调与内部评审作为红线核对清单使用。任何设计变更若触碰其中之一，须升级评审。

|**\#**|**工程不变量**|**违反后果**|
|---|---|---|
|1|**中心永不排序**|重建中心化派单引擎，承担撮合责任，中心算力随单量上涨，成本优势归零|
|2|**中心不抽佣**|触发与在位巨头相同的 P\&L 自我颠覆结构性矛盾|
|3|**A2A 只服务计划性出行**|薄中心坍塌，被迫重建厚中心，产品命题报废|
|4|**边缘是责任边界**|若把 Agent 决策责任收回中心，中心担责并变厚|
|5|**硬闸门二元、不许长成评分**|以安全为名给司机排名，中心变厚|
|6|**中心只摄派生事实**|汇聚原始视频 / 轨迹则触 PIPL 合规雷并破坏薄|
|7|**协议非护城河**|押注协议保密，标准开放后竞争力归零|
|8|**冷启动辅助轮须有下线里程碑**|临时中央撮合器长成永久厚中心|



# 10　AI 原生工程方法（开发实现）

本章回答尽调中的团队可规模性之问：一支精干团队如何交付并持续演进这套系统？答案是工程方法本身也是 AI 原生的。

## 10\.1　Agent 即软件构件

系统以声明式能力描述组织：每个 Agent 声明自己的能力与策略接口，彼此通过 A2A 协议组合。新增一类供给（例如 Robotaxi）等于接入一个会说协议的新 Agent，而不需要改动中心逻辑。这从根上降低了系统的耦合与回归面。

## 10\.2　AI 辅助研发流程

编码、评审、测试与文档大量借助 AI Agent 完成，使小团队获得高交付杠杆。这不是锦上添花，而是这套系统能由精干团队交付的工程前提——也是回应团队可规模性质疑的实质论据。

## 10\.3　评测驱动（eval\-driven）

Agent 行为（尤其协商策略）以评测集回归：变更须通过既定评测基线方可上线，避免改好一处、悄悄改坏三处。可观测性覆盖每个 Agent 的决策链路与 LLM 调用率。

## 10\.4　部署拓扑与冷启动

部署上，云端运行多租户隔离的 Agent 进程，外加薄中心服务（身份 / 会合 / 清算 / 审计），二者均可水平扩展。冷启动采用现成的捕获式路径：以已合规的自有车队作为过滤后的初始供给，叠加已验证的 B 端机构需求，提供初期协商所需的流动性密度；若临时引入中央撮合辅助轮，必须按不变量 8 标注下线里程碑。
